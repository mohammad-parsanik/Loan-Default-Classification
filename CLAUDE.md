# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

A bank early-warning system that predicts the **worst delinquency class over the next 6 months** (4 classes: 0 = No Delay, 1 = Current/Minor Delay, 2 = Past Due+, 3 = Severe Past Due). Records are monthly point-in-time snapshots of an upstream ETL table (64 numeric per-loan features, no categoricals; the column set is pinned in `contract/columns.json`).

**Prediction is per LOAN** (`LOAN_ID` × `SNAPSHOT_DATE`) as of July 26, 2026 — business asked for risk on each individual facility. This is the ETL's native grain: `WORST_FUTURE_CAT` is already computed per loan upstream (`MAX(LABEL_DPD) GROUP BY LOAN_ID`), and the customer rollup was applied in Python, so the switch removed a groupby rather than adding a labelling scheme. `PREDICTION_GRAIN` in `project_config.py` still switches back to `"portfolio"` (one row per `NATIONAL_CODE`, label = max over the customer's loans) — that is what `results_1`…`results_6` were measured under, and it is the rollback path. Delete the portfolio path once loan grain is accepted.

**The deliverable is a ranked API queue** (July 2026 reframe): loans not yet severe (`current_cat < 3`), ranked by calibrated+masked P(entering class 3), consumed by an enrichment API at 240 requests/hour (`API_RATE_PER_HOUR`). Already-severe loans are rule-flagged, never ranked — but at loan grain their still-healthy siblings stay in the queue, which is the point: a customer already in distress on one facility is not a low-risk customer on the others. (Under portfolio grain `current_cat` was the portfolio MAX, so one severe loan carved out the whole customer.) The API is keyed by `NATIONAL_CODE`, so two loans of one customer occupy two queue slots but cost one call — `recall@K` is therefore slightly conservative, which is the safe direction; `score_instances` logs the duplicate-customer count in the callable window so the gap can't drift unnoticed. **Headline metric: `ranking` block (recall/lift at K-hours, PR-AUC) from `full_evaluation`**, cost-matrix-free by design — the `COST_MATRIX` values are guessed (business gave the 4× anchor only; the class-3 row is extrapolated), so cost is a secondary diagnostic, never the target. The enrichment API returns present-time data only (cannot backtest past calls), so API value is only assessable forward.

**Key label property:** `WORST_FUTURE_CAT` includes the current month ⇒ `label >= current_cat` always (a loan can't improve past its current category). Not leakage — a definition. Exploited via `decision.mask_monotone` (zero impossible probability mass) and per-current-cat calibration (`StratifiedCalibrator`). It also makes already-delinquent slices mechanically easy — judge models on the `current_cat_0` slice and the ranking block, never aggregate F1.

Frames are projected to it **by name** (`DataLoader.project_features`): missing feature ⇒ raise, unknown column ⇒ warn and drop. It holds no column semantics on purpose (public repo).

On this Mac you can read/edit code but cannot execute the pipeline or load data.
- **The current baseline is `results_7/`** (Run 7, 2026-09-05: loan grain, ≤7B population, deployed multiclass arm — pooled ranking AP 0.6555, cat_0 slice AP 0.1460, severe base rate 0.0903; see `AGENT_HANDOFF.md` §23). It holds a partial console log plus `clip_impact.csv`; the run's `metrics.json` / plots / bundle are still on the server at `artifacts/20260905_133423/`. `results_1/`…`results_6/` are historical only — **never compare against them** (§20: features changed meaning; §21: the population widened). `explore_output/iv_report.csv` has the IV analysis and is stale. **Read Run 7's numbers against `AGENT_HANDOFF.md` §24:** the severe base rate runs 8.37% → 9.96% → 12.95% across the train / gap-dropped / test snapshot windows, because the upstream installment table is hard-deleted for closed and post-NPL loans and every snapshot was rebuilt from one as-of view — so old snapshots are depleted of exactly the class-3 rows. Ranking survives it (isotonic is monotone); calibrated probabilities, `PREDICTED_CLASS` and `EXPECTED_COST` are biased low.
- **Data is cached one snapshot per NPZ**, under `data/snapshots/<stage>_<key>/<snapshot>.npz` (+ a `.manifest.json` each), where `<key>` is the schema hash from `_cache_key`. Bump `DATA_VERSION` in `project_config.py` to invalidate; the key also covers the contract version and the feature list **in order**, so a contract change invalidates it on its own. Files are written with `np.savez` (uncompressed) — at the ≤7B population `features_flat` is several GB and zlib over it cost tens of minutes per rebuild.
- **Why per snapshot:** the ETL recomputes the newest 7 snapshots on each monthly load — T is new, T-7 has just matured, the five between are rewritten without changing anything the ML side reads. So a **matured snapshot never changes again** and its NPZ is permanent (next month's training run reads one new snapshot from the DB and the rest from disk), while an **immature snapshot is provisional**: `load_pred_portfolios` reuses its cache only while the ETL cycle that built it is still the newest successful run in `etl_job_control`, and re-reads from the DB whenever that ledger is unreadable. Training reads mature snapshots only, so a newly matured snapshot is simply a file that is not there yet.
- **Diagnostics read the cache through `data_loader.load_cached_arrays()`**, which concatenates the per-snapshot NPZs and rebases `offsets`. `explore_iv_woe.py` / `explore_umap.py` / `explore_clip_impact.py` take `--cache_dir` (default: the current schema's) instead of the retired monolithic `train_portfolios_cache.npz`.

## Pipeline architecture (run.py)

Load (per-snapshot NPZ cache, one `SELECT` per mature snapshot; project columns by name, canonical row sort, feed-invariant checks) → temporal split (or walk-forward folds) → per fold: preprocessing (fit on train only: impute → clip [1,99]pct → RobustScaler) → **model arms** (XGBoost variants on `build_features` output — 64 raw features at loan grain, or min/max/mean/std per feature + loan count = 257 at portfolio grain; see `MODEL_ARMS`) → per-arm stratified calibration + `full_evaluation` → deployed-arm selection (best pooled ranking PR-AUC among full-distribution arms) → CI + plots (incl. all-arm capture curves) + `model_arm.pkl`/`calibrator.pkl` deployment artifacts + `arms_metrics.json`.

**The DeepSets+XGB neural pipeline is legacy** (`DEEPSETS_ENABLED=False`): the Run-5 shootout showed plain XGBoost on the aggregated features beats it on every ranking slice (pooled AP 0.567-0.574 vs 0.541; cat_0 slice 0.176-0.179 vs 0.127). Its code path (`_train_deepsets_legacy` in run.py, trainer, meta-learner, bundle) is intact behind the flag. If ever re-enabled, fix the LR schedule first — the warm restart at epoch 10 ate the fine-tuning phase (see results_5 training curves).

**Order independence (Aug 2026).** Nothing in the pipeline may produce a different answer because rows or columns arrived in a different order — the ETL's clustered PK is defence in depth, not a load-bearing assumption. Four mechanisms, all regression-tested in `tests/test_order_independence.py`:
- **Columns by name.** `DataLoader.project_features(df, order)` reindexes to an explicit list — `FEATURE_ORDER` when training, the model's own saved `features` when scoring (so an older model keeps working after the feed appends column 72). The three preprocessing transformers key every statistic by column POSITION, so this is what makes those indices mean what the fitted transformer thinks they mean; `preprocessing.assert_pipeline_features` checks it rather than trusting it, and `ModelLoader` refuses an artifact whose metadata cannot state its own feature order.
- **One canonical row order.** `process_raw_data` sorts each frame by `(NATIONAL_CODE, SNAPSHOT_DATE, DPD_DAYS desc, LOAN_ID)`; since Sept 2026 it is fed one snapshot at a time, so the instance list is ordered `(SNAPSHOT_DATE, NATIONAL_CODE, DPD_DAYS desc, LOAN_ID)` — snapshot-major rather than customer-major. Either is fine and the swap was deliberate; **what matters is that the order is a function of the data and not of arrival order**, and that `LOAN_ID` makes the key unique so no tie survives to inherit it. This is also what makes XGBoost's index-based `subsample`/`colsample_bytree` reproducible — **do not "fix" that by removing the sampling**, the sampling was never the problem. Note it means a run before Sept 2026 and one after draw different subsamples from identical data.
- **Explicit tie-breaks** in the queue (`score_instances` sorts on `_flagged, RISK_SCORE, NATIONAL_CODE, LOAN_ID`) and in the ranking metrics (`ranking_metrics(..., tie_break=)`, `capture_curve(..., tie_break=)`, fed LOAN_ID by `run.py`). Calibrated probabilities tie in large blocks — isotonic regression is a step function — so a merely *stable* sort left "who gets called today" to how SQL Server laid the rows out.
- **The cache sees column identity** — `_cache_key` hashes `CONTRACT_VERSION` and the ordered feature list.

Key behavioral toggles in `project_config.py`:
- `OPTIMIZE_ON_VALIDATION` + `VAL_SPLIT_MODE` — current default is `True` + `"customer"`: an in-time, customer-disjoint 20% holdout (stable md5 of `NATIONAL_CODE`) drives early stopping + Optuna without touching the test label window, and is then reused to fit the probability calibrator (final XGB trains on the 80% only). `VAL_SPLIT_MODE="temporal"` is the legacy leaky mode (val/test label windows overlap 5 months — Run 2). `OPTIMIZE_ON_VALIDATION=False` = no val set, `FIXED_EPOCHS` + fixed XGB params (Run 3 mode).
- `COST_MATRIX` — single source of truth for costs (DeepSets loss, expected-cost `PREDICTED_CLASS` in `src/evaluation/decision.py`, `avg_cost` metric). Class decisions use `argmin(probs @ COST_MATRIX)`; the queue RANKING does not use costs (see above). **Training-time vs. inference-time, and why:** training-time cost weighting was found to hurt ranking (Run 5: the cost-free binary comparator beat the cost-loss-trained DeepSets on every slice; Run 6: turning `BASELINE_COST_WEIGHTS` off gained +1pt AP for multiclass) — so it's off now (`BASELINE_COST_WEIGHTS=False`, and the one model that ever used a cost-sensitive *loss*, DeepSets, is disabled via `DEEPSETS_ENABLED=False`). At inference the matrix still feeds `PREDICTED_CLASS`/`EXPECTED_COST` only — never `RISK_SCORE` — so there's no conflict between the two: nothing costs-related touches training or ranking in the deployed pipeline, only two secondary output columns. `decision.py`'s cost-matrix functions also accept an optional `cost_matrix=` override per call (see `ScoringParams.cost_matrix`) — needed because the module-level constant can't otherwise be changed without editing `project_config.py`.
- `PREDICTION_GRAIN` — `"loan"` (default) or `"portfolio"`. Decides what one scored row IS, end to end: `process_raw_data` emits one instance per row vs. per customer, `build_features` skips vs. applies min/max/mean/std aggregation, and the queue ranks loans vs. customers. It is part of the NPZ cache key, so the two grains cache separately. (`DATA_VERSION` was bumped to `v1.3` for this change; it is `v1.5` now — see the population note above.)
- `TRAIN_WINDOW_SNAPSHOTS` — `None` (default) trains on every snapshot clearing the 6-month gap; positive N keeps the newest N, negative N the oldest N. Purely the §24 recency A/B (does upstream deletion cost ranking, or only calibration?) — it discards training data by design, so leave it `None` for production.
- `EXPOSURE_FEATURE` (`REMAINING_AMNT`) — the deployed arm's ranking block is also cut by decile of this, as `ranking_by_exposure`. It is the amount-banding test: flat lift@K across deciles means a banded model buys nothing, since a base-rate shift is one tree split. Read `pr_auc`/`lift`, not `recall` — K is the full API budget spent inside one decile.
- `CARVE_CURRENT_CAT_GE` / `API_RATE_PER_HOUR` / `RANKING_REF_WINDOWS` — define the ranked-queue population and the K values (K = rate × window hours) reported by `src/evaluation/ranking.py`.
- `CALIBRATION_MIN_STRATUM_N` — per-current-cat calibration floor; smaller strata fall back to the pooled calibrator. **Precisely what "per-current-cat" means** (`StratifiedCalibrator` in `src/evaluation/calibration.py`): the fitting *sample* for each stratum is grouped by the customer's `current_cat` ALONE — never by predicted class. Within each stratum, one isotonic curve is fit per output class (`PerClassIsotonicCalibrator`, one-vs-rest over the 4 class-probability columns) — that's a per-class *curve*, not a second grouping dimension for which rows participate.
- `MODEL_ARMS` / `DEPLOY_ARM` / `DEEPSETS_ENABLED` — the arms lineup ("multiclass", "binary", "ordinal", "per_cat"; builders in `aggregated_xgboost.ARM_BUILDERS`), how the deployed arm is picked ("auto" = best pooled ranking AP among full-distribution arms; a final fit needs an explicit name), and the legacy neural arm toggle. `DEPLOY_ARM` is **locked to `"multiclass"`** after the Run-6 shootout (all four arms within ~1pt AP; multiclass best pooled and best on the cat_0 slice). **Run 7 contradicts that lock and it is the top open question**: on the ≤7B loan-grain feed `per_cat` wins pooled AP (0.6721 vs 0.6555) *and* the cat_0 slice (0.1780 vs 0.1460) — under `"auto"` this run would have deployed `per_cat`. Do not flip it on one snapshot; settle it with a 2-arm walk-forward (`AGENT_HANDOFF.md` §23 and §18 item 2). The "binary" arm is a ranking-ceiling diagnostic only — never deployed (business requires per-class probabilities; queue still sorts by P3).
- `ARM_OPTUNA_TRIALS` — 0 = arms use `XGB_DEFAULTS`; >0 tunes the deployed arm's XGBoost on val PR-AUC of P(severe) (`tune_arm_params`, lazy optuna). Only arms that could deploy are tuned.
- **Arm interface (July 10):** arms train/predict on precomputed `(X, y, current_cat)` arrays, not raw instance lists — `aggregated_xgboost.build_features(instances)` is called ONCE per split (train/val/test) in `run.py` and the same arrays are shared across every arm. `build_features` dispatches on the grain: portfolio → `aggregate_features` (257 cols), loan → the raw feature matrix unchanged (64 cols). Aggregating at loan grain would emit `min == max == mean == feature`, `std == 0`, `count == 1` — 4× the columns for zero information — so it is skipped, making X ~4× smaller. It replaced a per-arm Python loop (`_aggregate`, one instance at a time) that alone cost ~6.5 min/call at 6M rows; called ~12-13× across 4 arms it dominated a run's wall time. `aggregate_features` is vectorized (flat loan matrix + `np.reduceat`) and unit-tested against the old per-instance computation for exact equivalence.
- `VAL_SPLIT_MODE` — must stay `"customer"`. Ten of the 64 features are customer-level and identical across every loan a borrower holds; a random split leaks them across the fold boundary. Correctness, not preference.
- `WALK_FORWARD_ENABLED` — currently `False`. With **23 mature snapshots (2024-04-19…2026-02-19, as of Run 7)** and the load stage now cached per snapshot, a fold costs roughly preprocessing + arms + eval (~30 min for two arms), not the ~1.5-2h it once did. It is the recommended way to settle the `DEPLOY_ARM` question above.
- `PRED_SNAPSHOT_DATES` — snapshot(s) `predict` scores (int or list[int], overridden by `--snapshot_date`). `None` (default) auto-selects every currently-immature snapshot in `TRAIN_TABLE`; a requested date absent from the table is dropped (warn) and falls back the same way. There is no separate prediction table — `TRAIN_TABLE` holds both matured and not-yet-matured snapshots, and `Predictor` strips `WORST_FUTURE_CAT`/`WORST_FUTURE_DPD` before scoring since those columns hold a degenerate (not real) value on immature rows.

Stage checkpointing: each stage writes `<run_dir>/stages/<stage>.done` + a pickle, `--resume` skips completed stages. **Only the genuinely expensive stages are checkpointed** (per-arm training, DeepSets) — `load_data`/`split`/`preprocessing` deliberately are NOT: pickling 6-12M+ per-instance dicts via joblib used to cost 15-30+ minutes to save (and as long to load back) per stage, while recomputing them is ~30s/~20s/~4min thanks to the NPZ cache + cheap vectorized ops — so `--resume` just always redoes those three and skips straight to whichever arm wasn't finished. **Careful:** resuming after a config change silently reuses artifacts produced under the old config. Run dirs from before July 2026 (DATA_VERSION v1.0) are not resumable — instance dicts lack `current_cat`.

## Gotchas that matter

- **`LABEL_HORIZON_DATE` (column 71) must never become a feature.** It is a meta column by construction (`role: "meta"` in the contract), which is the whole reason `META_COLS` is derived rather than hand-written. If it ever leaks into `FEATURE_COLS` nothing raises — the model just gets quietly better on the training set, because the column is a monotonically increasing date that proxies snapshot recency and correlates with label maturity.
- **Label maturity is read, not computed.** `filter_mature_snapshots` compares `LABEL_HORIZON_DATE <= today` (both Gregorian `YYYYMMDD` ints) using a snapshot→horizon map populated by `DataLoader` from the feed and carried in the NPZ manifest. It falls back to the old `LABEL_HORIZON_MONTHS` calendar rule (with a warning) only when no horizon is known — synthetic frames, pre-v1.4 caches. The horizon is derived upstream on a different calendar, so the two can disagree at month boundaries. **Every** path that reads `WORST_FUTURE_CAT`/`_DPD` must filter through this: immature rows carry a well-formed, non-null, systematically optimistic label with nothing in the value to reveal it.
- **Clipping is the only preprocessing step the model can feel.** Median imputation and `PortfolioRobustScaler` are monotone and XGBoost splits on order, so they are invisible to it; `OutlierClipper` merges every value above p99 into one number and destroys the ordering there permanently. That makes it the step to re-check whenever a feature's distribution moves — `explore_clip_impact.py` reports `tail_lift = P(severe | x > p99) / P(severe)` per column, and a value above ~1.5 means the clip is deleting signal. Do not act on that number alone: exempting a column hands the model an unbounded feature, which is what clipping was for. A/B on validation lift@K. Changing a `clip` flag in `contract/columns.json` bumps `contract_version`, which invalidates the cache by itself. **Two known blind spots in the tool** (§23): `tail_lift` is computed over ALL mature rows rather than the ranked `current_cat < 3` population, so the whole DPD family reads at the arithmetic ceiling 1/base_rate and is measuring `label >= current_cat`, not signal; and nothing measures the p1 side, where `PAYED_OVERDUE_INST_CNT` (`p1=3`) and `HIST_MAX_DPD_DAYS` (`p1=1`) collapse the clean end of the distribution. **Both are now fixed** — `explore_clip_impact.py` takes `--ranked_only` and reports a `head_lift` for the p1 side; re-run it and re-read the DPD family, whose old numbers were measuring the label identity. **One real defect found and fixed:** `COUNT_90PLUS_DPD_LAST_3M` had `p1 == p99 == 0`, so the clip reduced it to a constant in every arm; it and the eight other bounded integer counts are now `clip: false` (**contract v2** — see `AGENT_HANDOFF.md` §24 and `_LOCAL_OVERRIDES` in `src/data/column_contract.py`, which records the deliberate divergence from the vendored ETL copy until upstream mirrors it).
- **The four `DAYS_SINCE_LAST_*` columns carry a `99999` sentinel** meaning "never reached this band", opposite `0` = "in that band right now". They are exempt from `OutlierClipper` and `PortfolioRobustScaler` via the contract's `clip: false, scale: false`. Never impute the sentinel to a median. The bug this prevents is invisible in the columns where "never" is the majority (p99 *is* the sentinel, clipping is a no-op) and destructive in the ones where it is a minority — spot-checking one column proves nothing about its siblings.
- **`assert_feed_invariants` (`src/data/feed_checks.py`) runs on every DB load** and logs (does not raise) violations of the feed's row-level guarantees. Its self-check runs with `python -m src.data.feed_checks`.

- **Active model is `src/baselines/aggregated_xgboost.py`** (arm `"multiclass"`, locked in `DEPLOY_ARM`). `src/model/deep_sets.py` is the legacy neural path, dead by default (`DEEPSETS_ENABLED=False`) after losing the Run-6 arms shootout on every ranking slice. The trainer class is named `TransformerTrainer` but only runs when DeepSets is re-enabled — there is no Set-Transformer; `src/model/set_transformer.py` was deleted July 26, 2026 (never imported by `run.py`).
- `MAX_LOANS_PER_CUSTOMER` resolves at runtime to **2** (99th percentile) at portfolio grain, and to **1** at loan grain (Run 7 confirms). Most customers have 1 loan — this is why DeepSets ≈ baseline and why attention was abandoned. **At loan grain it is inert** (every instance holds one loan, nothing to truncate); it still gates the DeepSets padding width, and `DEEPSETS_ENABLED` now raises unless `PREDICTION_GRAIN="portfolio"` — a set encoder over one-element sets is just an MLP.
- **Train/serve truncation skew (FIXED July 26, 2026):** training aggregated over the FULL portfolio (`run.py` loads with `max_loans=None`) while inference truncated to the stored 99th-pct `max_loans`, so customers above the cap were scored on min/max/mean/std computed over a DPD-ranked subset of the loans the model was fit on. Silent — no error, and `LOAN_COUNT` stayed correct because `aggregate_features` reads the untruncated `inst["n_loans"]`. `ArmScorer` never used the `max_loans` it stored; the cap leaked out via `scorer.max_loans` at each call site. Now one attribute, `truncate_loans`: `None` for `ArmScorer`, `max_loans` for `DeepSetsScorer`. Measured impact on a 3-loan synthetic customer: `P_PAST_DUE` 0.684 → 0.267.
- **`ranking_single_loan` is a within-run slice, NOT a cross-run comparison.** It was added (July 2026) to compare a loan-grain run against `results_3`…`results_6`, because single-loan customers produce identical rows under either grain while the headline `ranking` block does not — loan grain changes the population and the severe base rate, and PR-AUC moves with the base rate regardless of model quality. **The ≤7B widening (§21) killed that use**: the slice controls for grain, not for population, so it has no power against the old runs either. It is still the cleanest read of what the grain change did *within* one run. Note `full_evaluation` writes it to `metrics.json` but `run.py` does not log it. `ranking.base_rate` sits next to `pr_auc` so any base-rate shift stays visible.
- Truncation to MAX_LOANS sorts by `DPD_DAYS` desc (a prediction-time feature). It previously sorted by the label `WORST_FUTURE_DPD` — fixed July 2026; do not reintroduce label columns into `process_raw_data` sorting. The label is `max` over ALL loans while features keep only the first MAX_LOANS; each instance also carries `current_cat` (current worst category, drives stratified evaluation).
- Temporal split usability is computed against `date.today()` (`temporal_split._get_usable_snapshots`) — the same code produces different splits as calendar time passes. Snapshot dates are floats like `20241021.0`.
- Labels: features keep 5-category granularity; the target is capped at `config.NUM_CLASSES` classes (`min(max(cat), NUM_CLASSES - 1)`, currently 4: raw cats 0/1/2 pass through 1:1, raw cats 3-4 collapse into class 3). For already-delinquent customers the label is largely mechanical DPD accrual — judge models on the `current_cat_0` slice (`by_current_cat` metrics), not aggregate F1.
- **Deployment (see `DEPLOYMENT.md`):** `train_single_fold` writes the deployed arm's artifacts per-file (`model_arm.pkl`, `scaler.pkl`, `calibrator.pkl`, `metadata.json`) AND as a single-file `model_bundle.pkl` (kind=`"arm"`: scaler + arm + calibrator + metadata). `ModelLoader`/`Predictor` load from either the fold directory OR the bundle file. `train --final` fits `DEPLOY_ARM` on all mature snapshots and emits the bundle to ship. The legacy DeepSets bundle (when `DEEPSETS_ENABLED`) is written separately as `deepsets_bundle.pkl`.
- `explore_output/iv_report.csv` is **stale**: the old IV binning forced IV=0.0 for ~10 skewed/binary features (they are NOT constant — DB-verified). Re-run `explore_iv_woe.py` against the current cache (it has been stale across the v1.1 → v1.5 rebuilds and was not re-run for Run 7).
- `Predictor` output: `RISK_RANK` (queue position, NaN for flagged rows), `LOAN_ID` (the scored row's loan; None at portfolio grain), `RISK_SCORE` = calibrated+masked P(severe), `RULE_FLAG` ∈ {"", ALREADY_SEVERE, SUPERSEDED, PREDICTED_SEVERE, RECENTLY_CALLED}, `N_LOANS_IN_PORTFOLIO` (the customer's TRUE loan count, not the rows in this instance), `CUSTOMER_MAX_RISK_SCORE` (worst loan per customer — context for consumers deciding about the customer as a whole; the queue still ranks per row), `EXPECTED_COST` (secondary). When several snapshots are scored, `PRED_DEDUP_LATEST` keeps only each customer's newest row in the queue (stale scores waste API budget — the API can't be queried "as of" the past). That dedup stays keyed on `NATIONAL_CODE` even at loan grain, and deliberately so: the API is customer-keyed, so any newer row makes the customer's older rows stale for calling purposes. Same for `RECENTLY_CALLED`. Do not "fix" either to `LOAN_ID`. `--called_log <csv>` (NATIONAL_CODE, CALLED_AT) flags customers called within `API_DATA_TTL_DAYS` (~30d, business-confirmed freshness window). `CERTAINTY_ACT_THRESHOLD` (default None = off, pending business decision) flags near-certain P(severe) rows to act on directly, reserving API calls for uncertain cases.
- **Inference architecture:** `ModelLoader.load_pipeline()` returns `(scorer, calibrator, features)`. A `Scorer` abstracts the model family — `ArmScorer` (scale → `aggregate_features` → `arm.predict_proba`; the deployed path, no torch) or `DeepSetsScorer` (legacy embeddings → meta-learner). `Predictor.predict()` (DB-backed) and `score_dataframe()` (DB-free, takes a caller-supplied DataFrame) both funnel through the shared `score_instances()` transform in `predictor.py` — single source of truth for the calibrate → mask → queue-flag → rank pipeline. The directory loader prefers `model_arm.pkl`, falling back to DeepSets artifacts.
- **Manager-code integration (`src/inference/scoring.py`):** `run_scoring(df, params)` is the recommended entry point for another codebase that owns its own data sourcing (possibly several sources) and needs explicit, per-call-overridable business knobs instead of reaching into `project_config.py` globals. `ScoringParams` (`scoring_params.py`) holds every knob `score_instances` needs (`cost_matrix`, `carve_current_cat_ge`, `certainty_act_threshold`, `api_data_ttl_days`, `pred_dedup_latest`, `called_log_path`, plus `calibration_df`/`output_path` which have no config equivalent); `.resolve()` fills any unset field from `project_config` and logs one `logger.warning` naming exactly which fields defaulted, so an integrator who forgot a parameter sees it in the logs. `bundle_path` is the one required field — no project-wide default makes sense for "which trained model."
- **Standalone deployment:** `build_scoring_package.py --bundle <model_bundle.pkl> --output <dir>` copies just the ~21 files scoring needs (including `contract/columns.json`) (no `run.py`, no `src/model/*` DeepSets code, no torch/optuna/umap) into a self-contained folder with its own `requirements-scoring.txt`, for handing scoring to a system that shouldn't depend on this whole repo. Regression-tested by actually running scored output in a subprocess with this repo off `sys.path` and torch/optuna/pyodbc import-blocked (`test_build_scoring_package_runs_standalone`). See `DEPLOYMENT.md` §4.
- The evaluation run also trains a **binary severe-event comparator** (`BinarySevereBaseline`, same 257 aggregated features, `binary:logistic`) — its `binary_ranking` block vs the multiclass `ranking` block answers whether the multiclass pipeline costs ranking quality, and informs the deferred per-current-cat-models idea.
